### FR.31 — Attachments

Daemon storage, the attachment methods and the web upload were built 2026-11-15 (merge `98fa1f4`; the web upload is live since the 2026-11-15 deploy, decision A19). The desktop drag-and-drop and file mode (FR.31.2) was built the same day (merge `f139a19`). Design: `docs/features/focus-references-attachments-previews.md` section 3. Reports: `.wpf-work/300-attachments-daemon.md`, `300b-attachments-fixes.md`, `310b-recheck-attachments.md`. (FR.27-FR.30 are reserved by the WPF programme plan: browser pane, output modes, multi-screen layout, helper models.)

- **FR.31.1 — Storage.** [DONE] Attachments are stored per profile in app data (decision A12): `%AppData%\TessynDesktop\attachments\<profileKey>\<nodeId>\<yyyyMMdd-HHmmss>-<safe name>`. `profileKey` is the session's resolved profile (`default` for the Default profile, else `ClaudeProfileModel.ProfileId`). The timestamp is UTC. A name collision in the same second gets `-2`, `-3` before the extension. A file is written as `<guid>.part` first and moved in, so a failed write leaves nothing in the list. Nothing is deleted automatically; the files stay until someone removes them. The `attachmentId` is `att.` + base64url of `<profileKey>/<nodeId>/<file name>`: it holds no state and survives restarts.
- **FR.31.2 — Desktop.** [DONE] In the WPF client, files dropped onto the prompt input, or pasted with Ctrl+V from an Explorer file copy, follow the *File mode* toggle beside the input (paperclip icon). The toggle is global client state (`clients\wpf.json`). Off (default, path mode): the full path of each file or folder is inserted at the caret, one per line, replacing a selection. On (file mode): each file is copied through `attachment.import` (FR.31.6) into the session's attachments folder, one at a time, with progress and Cancel (a 10-minute call timeout), and `Attached file: <path>` is inserted, one line per file. If the text changed during the copy, the lines go on their own line at the end. A failed file inserts nothing and shows a notice; a folder is refused in file mode; names with control, format or line-separator characters are refused in both modes. Only real file paths (`DataFormats.FileDrop`) are handled. Cancel does not stop a copy the daemon has already started, so that copy may remain in the attachments folder.
- **FR.31.3 — Web.** [DONE] The input area has an attach button (paperclip, several files, uploaded one after the other, progress bar with Cancel). The browser sends `POST /api/attachments` (multipart: the `nodeId` field first, then the `file` part; the file is streamed, never buffered; at most 200 MB; the server computes its SHA-256) with the `X-Tessyn-Client: web` header and the login cookie. The server keeps the file in its blob store and asks the daemon, over the link, to fetch it (`attachment.fetch`). The daemon downloads `GET /link/blob/{blobId}` once with its link token, checks size and SHA-256, stores the file as an attachment and replies. The server then deletes its copy and answers `{ attachmentId, path, name, size, mime, createdUtc }`. The page inserts `Attached file: <path>` at the caret. `name` is the cleaned name without the timestamp prefix.
- **FR.31.4 — Session side.** [DONE] The prompt gets a plain path, for example `Attached file: C:\...\attachments\...\photo.png`. Sessions read it like any other file; no MCP change is needed.
- **FR.31.5 — Handles.** [DONE] An attachment is readable through `file.read` with the `attachmentId` as the handle, on the desktop and on the relay. See FR.31.8 for the rules that apply.
- **FR.31.6 — Methods.** `attachment.import { nodeId, sourcePath }` copies a local file into the session's attachments (loopback only; the relay answers `-32601`; a relative path resolves against the session's working directory). `attachment.list { nodeId }` lists the session's attachments, newest first, across its profile folders (loopback and relay; on the browser allowlist). `attachment.fetch { blobId, nodeId, name, size, sha256 }` is called only by the web server (relay only; not on the browser allowlist; a browser gets `-32601`). Wire formats: `docs/refactoring/tdcp-spec.md` section 9.8.
- **FR.31.7 — Limits and errors.**
  - One file is at most 200 MB (the upload, the fetch and the import).
  - At most 2 uploads run at the same time (`429` for a third).
  - The server's blob folder has a byte quota (1 GB by default). A full quota or a full disk answers `507`. The quota is checked before the body is read.
  - A blob is single-use. It is deleted when the response ends and by a sweep after 60 minutes. Blobs never live in memory.
  - The daemon waits at most 240 s for the download. The server waits 300 s. A daemon timeout is `504`, not `422`.
  - Other errors, all as `{ "error": "<message to show>" }`: `400` (not multipart, `nodeId` missing or after the file, no file, missing client header), `401` (not logged in), `413` (over the cap, answered before the body is read), `422` (the desktop refused: session not found, size or hash mismatch, an incomplete download), `502` (unreadable reply from the desktop), `503` (desktop offline, checked before the body is read).
  - File names: only the last path segment is kept; control and format characters (bidi, zero-width) are dropped; invalid characters become `_`; trailing dots and spaces are trimmed; reserved device names (`CON`, `COM1`, ...) get a `_` prefix; `.` and `..` are never a segment; an empty name becomes `file`; at most 120 characters with the extension kept (an extension over 16 characters counts as part of the name). A full path over 259 characters is refused with a clear message and nothing is left behind.
- **FR.31.8 — FileAccess interplay.** The attachments folder is an exception to the relay's working-directory rule (FR.23.18, decision A11): the relay may read a file below `attachments\<profile>\<node>\` for the own session. All other relay rules still apply: type allowlist (a `.zip` attachment is refused), per-type size caps, the chunk cap, the audit log and the denied list. The opened file's real path must be exactly `attachments\<profile>\<node>\<file>` and the file must have one hard link, on both transports; a junction or a second hard link name is refused. `attachment.import` applies the relay deny rules too (data root closed, every name rule), so it cannot copy a secret to where the relay can read it. It refuses a source that is another session's attachment (the own session may import its own file again), a file with more than one hard link, a non-local (UNC) path and a file over 200 MB.
- **FR.31.9 — Page security and deploy.** The Tessyn Web content security policy allows `img-src 'self' data: blob: https:` and `media-src 'self' blob: https:` (the other directives are unchanged). The media host allowlist is a daemon setting that the server cannot know, so the page enforces it, not the policy (see FR.26.4). nginx needs a `/api/attachments` location with `client_max_body_size 201m`, `proxy_request_buffering off` and 600 s timeouts. It is in `deploy/nginx-tessyn.vvinogradoff.com.conf` and was applied on the server 2026-11-15 (decision A19). On Linux the blob folder is created with mode 0700 and the files with 0600; the service unit runs with `PrivateTmp=true` and `UMask=0077` (already the case in `deploy/tessyn-web.service`), so the default blob folder under the temp directory is private to the service.

Status: FR.31.1-FR.31.9 implemented (FR.31.2 merged as `f139a19`, 2026-11-15).
