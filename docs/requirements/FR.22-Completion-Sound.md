### FR.22 — Focus Item Sound (formerly Session Completion Sound)

A per-session audible cue for the **Focus view** (FR.23): it plays when a **new Focus item** appears. The completion sound went off every so often (every finished interactive turn, up to once per 3 minutes per session) and mostly told the Architect nothing; a new Focus item is what needs attention, so it is now the only trigger. Neither the desktop toast nor Telegram announces turn completion (FR.21.5, ISSUE.012), and now the sound does not either.

**FR.22.1 — Trigger point:** The sound fires when an Attention Item is **newly created** in any session — any kind: `critical`, `ask`, `todo`, `alert` or `decided` (FR.23.2) — by `post_attention` or by the `notify_user` capture (FR.23.7), i.e. each outcome of `IAttentionService.Post` with `IsCreated == true`. It does **not** fire when:
- a turn completes, for any reason and in any mode (scheduler, orchestration, Telegram, interactive);
- an item is **updated** (a re-post that matches an open item by key or title, FR.23.4);
- an item is **resolved, answered or dismissed**, by the session or by the user.
Worker Sessions cannot post (FR.23.6), so they never make the sound. The sound is independent of the notification fan-out: a `critical` item (always notified, FR.23.4) or a `notify: true` post toasts and pings Telegram as before, and the sound follows the same rule as the other kinds — one sound per new item, no more.

**FR.22.2 — Per-session toggle:** `SessionNodeModel.PlayCompletionSound` (bool, default `true`) is kept as the stored and wire name (`session.setOptions`, `SessionOptionsDto.PlayCompletionSound`), so existing stored values keep their meaning: a session that had the sound off stays silent, one that had it on now plays it for its new Focus items. Only the user-facing text changed: in the WPF command bar the bell icon toggle has the tooltip "Play a sound when a new Focus item appears in this session." and the UI Automation name "Focus item sound". The switch of the session that **owns** the item decides; the daemon checks it before it publishes the event or plays, and the WPF client checks it again before it plays.

**FR.22.3 — Throttle:** No more than one sound per **burst**: a short, global window (`AppSettingsModel.SessionCompletionSoundThrottleSeconds`, default **3** seconds, shared by all sessions) so that one `post_attention` call with several items, or several sessions posting within seconds, give one sound. The window starts at the sound that was played; a new item inside it plays nothing. The previous default of 180 seconds belonged to the per-session completion sound: a stored value of 180 (the old default) is read as the new default of 3 seconds; any other stored value is used as it is. The daemon applies the window before it publishes the event, and the WPF client applies it again on its side.

**FR.22.4 — Sound source and playback:** `AppSettingsModel.SessionCompletionSoundFile` (string, default `%WINDIR%\Media\Windows Notify.wav`) names a `.wav` file (the setting keeps its name and value). `ISessionSoundService` plays it via the Win32 `winmm.dll` `PlaySound` API (`SND_ASYNC | SND_FILENAME`). Playback failures (missing file, no audio device) are logged and swallowed; they never fail or delay a post.

**FR.22.5 — Sound picker:** Settings → Notifications has a "Focus item sound" control group: a dropdown populated by `ISessionSoundService.GetAvailableSounds()` (every `.wav` under `%WINDIR%\Media\`), a **Test** button that plays the selected sound immediately (bypassing the throttle), and a numeric field "Throttle (seconds)" bound to `SessionCompletionSoundThrottleSeconds`.

**FR.22.6 — Who plays it (J2 sound channel):** A connected client that registered the `sound` channel (`client.register`, `notifications.local`) plays the sound itself; the daemon host stays silent for it. For each new item the daemon publishes the local-stream event `focus.itemCreated { nodeId, itemId, kind, raisedUtc }` (never relayed to the web), waits up to 3 seconds for `notification.ack { nodeId }` and plays the sound itself when no acknowledgement came, so that a hung or killed client never loses the sound. When no client registered the channel, the host plays at once. The client drops a replayed event older than `NotificationRaisedPayload.MaxReplayAge` (30 s) and acknowledges every event it handled, also when its own throttle kept it silent or the option is off, so a sound is never doubled and never lost.
