# TessynDesktop — Glossary

## Domain Terms

| Term | Definition |
|------|-----------|
| **Session** | A single continuous conversation with Claude Code. Represented as a Session node in the tree. Backed by one Session File on disk; its human-readable name is stored in `appsettings.json`. |
| **Session File** | A plain-text file storing the full message history of one Session. Named `YYYY-MM-dd-HHmm-{6_random_lowercase_alpha}.txt`. Located under the Session Files Root. |
| **Session Files Root** | The base directory where all Session Files are stored. Configurable in the Settings window. Default: `<AppData>/TessynDesktop/sessions/`. |
| **Directory Node** | A top-level tree node backed by a real filesystem directory. Its display name is the Auto-derived label of its path (FR.1.3), with the full path shown as a tooltip. Not renameable. Defines the working directory for all Sessions nested beneath it. |
| **Group Node** | A virtual intermediate tree node that exists only in `appsettings.json`. Has a user-defined name, no session, and no working directory of its own. Used to organise sessions within a Directory node. Renameable. |
| **Session Node** | A terminal tree node representing one Session. Its name is stored in `appsettings.json` bound to the Session File path. Renameable. |
| **Working Directory** | The filesystem path of the Directory Node that owns a Session, passed as the working directory when launching the `claude` process for that Session. |
| **Compaction** | The application-driven process (Auto-Compact, FR.11.6) that condenses a session's conversation history. The compaction prompt embeds the transcript to compact directly (sourced from the text Session File, not resumed via `--resume`) and runs as a stateless call, so it works correctly regardless of Cross-Profile Session Adoption hops or mixed Model Provider turns within the same session. TessynDesktop appends a `[COMPACTION]` separator entry to the Session File; all pre-compaction history above the separator is preserved and remains visible in the UI. |
| **appsettings.json** | The single JSON configuration file for the application. Persists the full tree structure (Directory, Group, and Session nodes with their metadata), Settings values, and window state. Written atomically on every save. |
| **stream-json** | The Claude Code CLI output format flag (`--output-format stream-json`) that causes `claude` to emit newline-delimited JSON events, which TessynDesktop parses to render structured conversation output. |
| **Auto-derived label** | The display name of a Directory node and the directory part of a Telegram Topic name, computed by `IDirectoryLabelService.GetLabel` as the last path segment, replacing a trailing Well-known project folder by its parent name (repeatedly), e.g. `C:\Projects\oDesk\HardStop\Code` → `HardStop` (FR.1.3). Pure string logic — no filesystem or git access; computed at display time, never persisted, never overridden by the user. Different directories may share a label; duplicates are prevented by path, not by label. (The former rule, based on the nearest `.git` root, is retired.) |
| **Well-known project folder** | A conventional project-structure folder name — `Code`, `Docs`, `Data` (case-insensitive; list in `Constants`, not user-configurable) — that carries no identity of its own, so as the last path segment the Auto-derived label uses its parent's name instead (FR.1.3). Not stripped when the parent is a drive designator (`C:\Code` → `Code`). |
| **Claude Session JSONL** | A `.jsonl` file stored by the Claude Code CLI at `~/.claude/projects/<slug>/<session-id>.jsonl`. Contains the full conversation history as newline-delimited JSON events (types: `user`, `assistant`, `system`, `progress`, `file-history-snapshot`, `queue-operation`, `pr-link`). This is Claude Code's native session storage format, distinct from TessynDesktop's plain-text Session Files. |
| **Project Slug** | A filesystem-safe identifier derived from a working directory path. All non-alphanumeric characters (except `-`) are replaced with `-`, and trailing path separators are trimmed. Used by Claude Code to organise session JSONL files under `~/.claude/projects/`. Example: `/Users/alice/Projects/my_app` → `-Users-alice-Projects-my-app`. |
| **Session Import** | The process of converting a Claude Session JSONL file into a TessynDesktop Session File and adding it to the session tree. The original Claude session ID is preserved, making the imported session immediately resumable via `--resume`. |
| **Claude Assist** | Lightweight Claude CLI calls (using `claude -p --tools "" --no-session-persistence --model haiku`) made by TessynDesktop for utility tasks such as generating session titles or performing semantic search across session summaries. These calls do not create sessions and do not execute tools. Titles it generates are persisted by the Cross-Project Search Index so they are never regenerated for the same session (FR.13.8). |
| **Node Id** | A stable GUID assigned to each Session node and persisted in `appsettings.json`. Unlike `ClaudeSessionId` (which churns on detach/compact), `NodeId` never changes and is the durable handle used by the scheduling and orchestration tools. |
| **Agent Token** | A random secret string stored on each Session node in `appsettings.json`. Passed as the `X-CMX-Token` HTTP header in the per-node `--mcp-config` file, allowing the in-process MCP server to identify which node is the caller. |
| **In-Process Agent MCP** | An HTTP MCP server (JSON-RPC 2.0, loopback-only) hosted inside the Avalonia app process. Exposes scheduling and orchestration tools to Claude processes launched by the app. Port and enabled state are configurable in `appsettings.json`. |
| **Scheduled Turn** | A claude turn that is triggered by the scheduler at a configured time/interval rather than by user input. Scheduled turns are written to the session file and picked up by the file watcher. |
| **Self-Wake** | A `schedule_wake` call that targets the calling session itself (no explicit `target`). The scheduled turn runs in the same session node, resuming the same `ClaudeSessionId`. A new node is never created. |
| **Delayed Send** | The UI counterpart to Self-Wake (FR.14.12): right-clicking the Send button (SessionView) opens a popup for a delay amount + unit (Minutes/Hours/Days); confirming registers a **Delay**-kind self-wake schedule for the composed input text instead of sending it immediately. Lands on the exact same scheduling engine as the `schedule_wake` MCP tool, so the eventual turn is indistinguishable from an agent-created schedule. |
| **Supervisor Session** | A Session that uses the orchestration tools to create and control worker sessions. |
| **Worker Session** | A persistent, resumable Session node in the tree that is created or targeted by a supervisor session via orchestration tools. |
| **Mailbox Delivery** | The Scheduled Turn that hands an async worker's result (`send_to_session` with `mode=async`) to its Supervisor Session (FR.15.3): a delay-0 schedule flagged `ScheduleModel.IsMailboxDelivery`, whose prompt carries one `[Worker finished] <name>` block per result. Results that arrive while a delivery is still pending — including the whole time the supervisor is busy, since a delivery is held rather than queued on the turn lock — are merged into it, so workers finishing close together cost the supervisor one turn (FR.15.12). |
| **Session Detachment** | The act of moving a session's `ClaudeSessionId` to `PriorClaudeSessionIds` and setting it to null. After detachment the JSONL file remains accessible in JSONL view mode but `--resume` is no longer used; the next prompt feeds the text Session File as context via `BuildContextPreamble`. Detachment occurs after Auto-Compact completes and when the user confirms the Terminate Session action (FR.11.8). |
| **Terminate Session** | The title-bar action button (&#x2672; icon) that immediately detaches the live JSONL session after a confirmation dialog. Previously called "Clear". Does not send any prompt to Claude — it simply performs Session Detachment and shows a status message in the Output Panel (FR.11.7). |
| **Cross-Profile Session Adoption** | The lookup-and-relocate step run before any `--resume` attempt: if a session's JSONL isn't found under the currently active profile's session store, every other profile (Default plus each profile directory, including removed ones) is searched for a matching `<slug>/<ClaudeSessionId>.jsonl`. If found elsewhere, the file is **moved** — not copied — into the active profile's store so `--resume` succeeds natively. Falls back to `BuildContextPreamble` text reconstruction only when the session isn't found anywhere (FR.11.13). |
| **Model Provider** | Enum value (`ModelProvider.Anthropic` or `ModelProvider.Ollama`) stored on each `ClaudeModelInfo`. Determines how the claude CLI subprocess is launched — Anthropic uses profile auth, proxy, and the full native tool/MCP surface; Ollama uses local endpoint routing with no profile auth and, for a tool-capable model, the directory's [[Local Tool Profile]] (FR.12.21) in place of the full tool/MCP surface. |
| **Local Model** | A model served by a locally running Ollama instance. Identified by `ModelProvider.Ollama` on `ClaudeModelInfo`. Routed by setting `ANTHROPIC_BASE_URL` (bare host), `ANTHROPIC_AUTH_TOKEN=ollama`, and `ANTHROPIC_API_KEY=""` on the subprocess. Does not use profiles (billing is local hardware). Because it is still the claude CLI being spawned, a tool-capable Ollama model receives the CLI's native tool/MCP surface over the Ollama-served Anthropic `/v1/messages` protocol exactly as an Anthropic model would — curated down by the [[Local Tool Profile]] (FR.12.21) when one is configured, since weaker/quantized local models are prone to mis-calling tools out of the full ~30-tool surface. |
| **ANTHROPIC_BASE_URL** | Environment variable that redirects the Claude SDK's HTTP client to a custom endpoint. Used by TessynDesktop to route sessions using Ollama models to `{OllamaBaseUrl}` — the **bare host, no `/v1` suffix** (the Anthropic SDK appends `/v1/messages` itself; adding `/v1` would double the path). When set, Ollama's Anthropic-compatible `/v1/messages` endpoint acts as a drop-in replacement for the Anthropic API, including honoring the `tools` parameter. |
| **Local Tool Profile** (`LocalToolProfileModel`) | A per-`DirectoryNodeModel` selection of exactly which native tools (`NativeTools`) and MCP servers (`IncludeCmxMcp`, `IncludedExternalMcpServerIds`) the claude CLI is given, applied only when the directory's selected model is local (FR.12.21). `null` (the default for existing/new directories) falls back to a lean default profile (`Read`/`Write`/`Edit`/`Bash`/`Glob`/`Grep`/`LS`, no MCP). Maps to `--tools "<names>"` and a curated `--mcp-config` (with `--strict-mcp-config`) on local turns. Has no effect on Anthropic-routed sessions. Also carries a master `Enabled` switch (FR.12.23, default `true`): when set `false`, the saved native-tool/MCP selection is preserved but ignored — `LocalToolProfileResolver.Resolve` returns `null` and the local model gets the same unrestricted tool/MCP access an Anthropic session would, until re-enabled. Controlled by an icon-style toggle button in the command bar, next to the Session Completion Sound button (FR.22) — short click flips `Enabled` and persists immediately, press-and-hold opens the checkbox-list popup without touching `Enabled` (FR.12.22, FR.12.23); visible only for local models, dimmed when `Enabled` is off. |
| **Model Tier** | An integer ranking (0–4) assigned to each model based on its capability family. Fable=4, Opus=3, Sonnet=2, Haiku=1, Local/Ollama=0. Determined by case-insensitive substring match on the model ID. Used by Model Tier Governance to prevent a lower-tier session from spawning a higher-tier worker. |
| **Model Tier Governance** | The enforcement rule (FR.16) that a session may only create or configure worker sessions with models at or below its own Model Tier. Enforced at `spawn_session`, `set_session_model`, `orchestrate_parallel`, and `orchestrate_pipeline`. |
| **Orchestration Budget** | An in-memory token ceiling registered for a single orchestration run (a `budgetTokens` arg on fan-out tools). Keyed by `(supervisorNodeId, orchestrationId)`. Accrues `input_tokens + output_tokens` from every worker turn. Spawning when exhausted returns an error. |
| **Orchestration Depth** | The nesting level of a session in a supervisor→worker chain. User-created sessions have depth 0. A session spawned by a depth-0 supervisor has depth 1. Capped at `Constants.Agent.MaxOrchestrationDepth` (default 5). Persisted in `SessionNodeModel.OrchestrationDepth`. |
| **Fan-Out** | Spawning multiple worker sessions concurrently, each handling one task or item. TessynDesktop supports two fan-out patterns: `orchestrate_parallel` (barrier — waits for all) and `orchestrate_pipeline` (non-blocking per item through sequential stages). |
| **Workflow Phase** | A progress marker written to the supervisor session file via `workflow_phase(title)`. Visible in the session view as a `[Phase: {title}]` system entry. Does not affect execution; used for progress tracking. |
| **Workflow Log** | A free-form progress message written to the supervisor session file via `workflow_log(message)`. Visible as a `[Log: {message}]` system entry. |
| **Output Format Guidance** | An optional `outputFormat` (free-text/markdown) argument on the orchestration tools, appended to the relevant prompt as advisory guidance on the desired response shape. Not validated or retried — replaces the earlier JSON-Schema-validated design, since a worker's result is consumed by another session that reads markdown far better than JSON. |
| **Worker Artifact File** | The convention that a worker producing a large or structured result (data, generated code, a big table) writes it to a file in its working directory and returns the file path instead of inlining the content in its markdown response. |
| **CMX Orchestration Skill** | The `cmx-orchestration` skill, provisioned by `SkillProvisioningService` into every registered profile's `skills/` folder. Documents supervisor behavior (choosing orchestration tools, output shaping, artifact files) and worker behavior (how to respond when spawned). Only its one-line description is always visible; the body loads on demand. |
| **Status Bar** | A narrow border docked at the very bottom of the main window (FR.18). Displays the selected model's ID and pricing on the left, and two vertically-stacked thin progress bars on the right showing the active profile's 5-hour session-window and 7-day rolling usage against Anthropic plan limits. |
| **OAuth Usage Endpoint** | Anthropic's private `GET https://api.anthropic.com/api/oauth/usage` endpoint (requires `anthropic-beta: oauth-2025-04-20` header). Returns `five_hour` and `seven_day` utilization percentages and reset times. Accepts the same `sk-ant-oat01-…` OAuth bearer token that Claude Code stores per profile in `.credentials.json`. |
| **Stale Usage Window** | A cached `five_hour` or `seven_day` usage snapshot whose reset instant (`FiveHourResetsAt`/`SevenDayResetsAt`) has already passed, meaning that rolling window has turned over since the snapshot was fetched and its percentage no longer describes the current window (FR.18.8). Detected and zeroed by `ClaudeUsageStalenessService` whenever a profile is selected, so the status bar never shows a percentage known to be out of date. The two windows are judged independently. |
| **Curated Model Catalog** | A built-in static list of Anthropic model IDs, display names, and per-1M pricing shipped with the app (FR.18.7). Replaces the previous dynamic CLI-based model enumeration. Ollama models are still discovered live and appended after the Anthropic entries. |
| **Auth Error State** (`HasAuthError`) | A per-session flag set when a `result`/`system` error event's content contains `"Invalid authentication credentials"` (FR.12.16). Drives visibility of the Re-authenticate and Remove buttons in the command bar. Cleared on request success, profile switch, or a completed reauth/remove action. |
| **OAuth Refresh Race** | A transient `claude` CLI failure (`Constants.Auth.OAuthRefreshRaceMarker`, exact text `"OAuth session expired and could not be refreshed"`) that occurs when two `claude` processes sharing one `CLAUDE_CONFIG_DIR` both attempt to refresh a near-expiry OAuth token at once — the loser presents an already-rotated refresh token. Not a real auth failure (the account stays valid). `TurnController` and `SessionTurnService` detect the marker and silently retry the turn once after `Constants.Auth.OAuthRefreshRaceRetryDelayMs`; `ClaudeProcessLauncher.Start` additionally serializes the `claude` process launch itself per config dir to narrow the collision window. See [[ISSUE.010]]. |
| **Removed Profile** | A profile taken out of the active `Profiles` list via the Remove action (FR.12.18). Its config directory is not deleted but renamed with a `_rem` suffix (e.g. `profile_4` → `profile_4_rem`), preserving its Claude sessions/projects for manual recovery while excluding it from the profile dropdown. |
| **Cross-Project Search Index** (`IClaudeSessionIndexService`) | A SQLite FTS5 full-text index over every Claude CLI session JSONL under `~/.claude/projects/*/` **and** under every Claude account profile's own config directory (`%AppData%/TessynDesktop/profiles/<profileId>/projects/*/`) — since a profile's sessions run with `CLAUDE_CONFIG_DIR` pointed at its own folder and never land under `~/.claude` (bug found and fixed 2026-07-27: the index originally scanned only `~/.claude/projects`, so any session run under a named profile was invisible to search). Plus a persisted title cache — both keyed by the session's stable external ID. Built and incrementally refreshed (by file mtime, plus an `IndexContentVersion` marker that forces a one-time full rebuild whenever the extracted content scope widens) in the background at app startup, and on demand. Indexes USER/ASSISTANT/tool-use-SYSTEM entries plus a TOOL_RESULT entry per `tool_result` block — the actual output of Read/Grep/Bash/WebFetch/Task-subagent calls, which carries most of a session's substantive content but was originally invisible to search (bug found and fixed 2026-09-11, see [[ISSUE.007]]). Exposes two distinct search shapes: `SearchAsync` (ranked by `bm25`, phrase-preferred, capped — for top-N results display) and `SearchMatchingSessionIdsAsync` (unranked, uncapped distinct-ID lookup — for membership tests like tree content-filtering, where a hard cap would silently hide genuine matches). Replaces the NodeJS `tessyn` daemon's cross-project search and server-side title generation (Stage 6 of the refactoring) with an in-process equivalent owned by `IDaemonClient`, so any future client (Avalonia, WPF, or a web client talking over TDCP) gets the same capability through the same contract (FR.13.15). |
| **Global Search** (`IsGlobalSearch`) | The import picker's toggle that switches search scope from the currently selected project only to every Claude CLI session on the machine, via the Cross-Project Search Index. Always available — unlike its daemon-backed predecessor, it has no external dependency (FR.13.15). |
| **Favorite Session** (`IsFavorite`) | A per-session flag, toggled via a star button in the command bar (left of the Model selector), that pins the session in the top-bar recent-sessions dropdown regardless of the 24-hour recency window or hidden state (FR.9.7). Displayed as a gold/black star in the dropdown row (replacing the hide icon while set), and as a display-only star in the session tree and Recent-tab list. |
| **One-shot Mode** | The default `claude` process execution model: one fresh process per turn, spawned with `-p`, given one message on stdin, then stdin is closed and the process exits on its own once the turn completes. The mode implicitly assumed everywhere in this document prior to FR.19. Contrast with Streaming Session Mode. |
| **Streaming Session Mode** (`IsStreamingMode`) | A per-session, opt-in alternative to One-shot Mode (FR.19): one `claude` process, spawned with `--input-format stream-json`, is kept alive across a session's turns instead of being respawned per turn. Toggled via a command-bar button beside the `--chrome` toggle; persisted per session (`SessionNodeModel.IsStreamingMode`). Because the process persists, native Claude Code background tasks and native scheduling function as designed instead of being discarded when a one-shot process exits — but the process does not survive Stop or an app restart. |
| **Persistent Session Process** | The single long-lived `claude` process backing a session in Streaming Session Mode. Owned by the streaming lifecycle manager, keyed by `NodeId`. At most one is alive per session at a time (FR.19.3); Stop terminates it outright (FR.19.5). When alive, a headless turn (scheduler/orchestration/Telegram) redirects into it rather than spawning a competing one-shot process (FR.19.13) — see Streaming Redirect. |
| **Streaming Redirect** (FR.19.13) | The rule that `SessionTurnService.RunTurnAsync` checks `IClaudeStreamingSessionManager.IsAlive(nodeId)` before falling back to One-shot Mode: if a Persistent Session Process is already alive for the target session, the headless turn is written to that process's open stdin instead. Fixes a confirmed context-divergence bug where a competing one-shot `--resume` process silently fell out of sync with the persistent process's own in-memory conversation state — see `docs/issues/ISSUE.006.streaming-headless-context-divergence.md`. The redirected turn's assistant/system output is written to the session file and UI by the process's existing primary event callback (owned by the `TurnController` that started it), not by `SessionTurnService` — a per-turn additive observer (`IClaudeStreamingSessionManager.SendTurnAsync`'s `onTurnEvent` parameter) is used only to build the headless caller's own `TurnResultModel`. |
| **External MCP Server Registry** | A settings-managed list of MCP servers (`AppSettingsModel.ExternalMcpServers`) merged into every session's `--mcp-config` alongside the in-process `cmx` server (FR.14.1, FR.20). Independent of claude.ai's own MCP connector registrations — a server usable via claude.ai is not automatically usable by a Tessyn session unless also registered here. |
| **MCP OAuth Client** | Tessyn's own OAuth 2.1 (PKCE) client role for `Http` + `OAuth2` registry entries (FR.20.3–FR.20.6): discovers or is given authorization/token endpoints, runs the interactive authorization-code flow via a loopback listener and the system browser, and stores/refreshes tokens locally — with no dependency on claude.ai's connector authentication. |
| **MCP Token Store** | The DPAPI-protected (`CurrentUser` scope) per-server token cache at `%AppData%\TessynDesktop\mcp-tokens\<Id>.token` (FR.20.5), holding the access/refresh tokens for `OAuth2` registry entries. Never stored in `appsettings.json`. |
| **Telegram Bridge** (`ITelegramBridgeService`) | The bidirectional link between Tessyn sessions and a Telegram bot (FR.21): mirrors each session's conversation into its topic (by default only each turn's final answer — Mirror Mode, FR.21.22), sends the user's only pings via `notify_user` (FR.21.3), and routes inbound Telegram replies and commands (including `/stop`, FR.21.11) back into the originating session. Excludes Worker Sessions outright (FR.21.19) — only the top-level session the user started ever reaches Telegram, even when it fans out dozens of workers as a Supervisor Session; pre-existing worker topics are deleted and their mappings cleaned up at each bridge start. A daemon client (FR.21.10) — depends on `IDaemonClient`, not `ISessionRegistry`/`ISessionTurnService`/`ISessionFileService` directly — making it a peer of the Avalonia UI on the daemon boundary rather than a registry-coupled service. Never announces turn completion by itself, and posts everything except `notify_user` silently (FR.21.21, ISSUE.012). |
| **Telegram Topic** | A Telegram **forum topic** — a threaded sub-conversation within a Topics-enabled supergroup, addressed by a `message_thread_id`. Tessyn creates one topic per session, lazily, the first time that session runs a turn while the bridge is enabled (FR.21.2) — never for sessions untouched since the bridge went live. Named `{Auto-derived label} / {session name}` (truncated to 128 characters); existing topics are renamed in the background at each bridge start whenever their Last-applied topic name differs from the current name (FR.21.18). |
| **Telegram Topic Map** | The persisted `AppSettingsModel.TelegramTopicThreadIdsByNodeId` (NodeId → `message_thread_id`), plus its in-memory reverse lookup, that lets an inbound Telegram message in a given topic be routed to the right session (FR.21.1, FR.21.4). |
| **Last-applied topic name** | The topic name Tessyn last successfully set for a session's Telegram Topic, persisted in `AppSettingsModel.TelegramTopicNamesByNodeId` (NodeId → name, untruncated; FR.21.1). Telegram cannot report a topic's current name, so this record is what topic name reconciliation (FR.21.18) compares against the current name to decide whether `editForumTopic` is needed. |
| **Telegram Token Store** (`ITelegramTokenStore`) | The DPAPI-protected (`CurrentUser` scope) single-file bot token cache at `%AppData%\TessynDesktop\telegram-token.dat` (FR.21.6). Never stored in `appsettings.json`. |
| **Universal I/O Mirror** | The mechanism (FR.21.9) by which every appended session entry — from either turn-execution path (interactive desktop, or headless scheduler/orchestration/Telegram) — reaches its session's Telegram topic. Taps a single point, `ISessionFileService.EntryAppended` (relayed through `IDaemonClient.EntryAppended`), rather than integrating with each turn path separately. Applies role-based prefixes (`USER:`, `⚙️`, none for assistant text), chunks long messages, skips empty `COMPACTION` markers, and suppresses the echo of a Telegram-originated reply back into its own topic. What it posts depends on the Mirror Mode (FR.21.22); every mirrored message is sent silently (FR.21.21); in Full mode a Mailbox Delivery is shortened to one line (FR.21.23). |
| **Mirror Mode** (`TelegramMirrorMode`) | The setting (FR.21.22, Settings → Telegram) that selects what the Universal I/O Mirror posts: `Full` (every entry), `AnswersOnly` (default — only the final assistant message of each turn, posted when the Turn Completed event arrives) or `Off`. `notify_user`, inbound routing and commands work in every mode. |
| **Turn Completed event** (`ISessionFileService.TurnCompleted`) | Raised once per turn, after the turn's last entry has been appended, by both turn paths — `SessionTurnService.RunTurnAsync` (headless) and `TurnController.SendAsyncCore` (interactive) — via `ISessionFileService.NotifyTurnCompleted` (FR.21.22). Carries whether the turn was cancelled and, when the turn ended in an error (e.g. a usage limit), the error text. Relayed as `IDaemonClient.TurnCompleted`; the Telegram Bridge uses it to post a turn's final answer — and its error text, so a usage-limit message always stays visible — in `AnswersOnly` Mirror Mode. Writes nothing to the session file. |
| **Telegram Mention Ping** | A `notify_user` message (FR.21.3) prefixed with `AppSettingsModel.TelegramMentionHandle` (FR.21.10, e.g. `@harmlessevil`) and sent with sound — the only kind of bridge message that is (FR.21.21). Distinguishes a ping meant to page the user from the Universal I/O Mirror's silent conversation text sharing the same topic. The automatic `✅ finished` completion ping it once also covered was removed (FR.21.5, ISSUE.012). |
| **notify_user tool** | The `mcp__cmx__notify_user` MCP tool (FR.21.3): lets a running session send an arbitrary message to the user's Telegram as a Telegram Mention Ping and, at the same time, as a Desktop Toast (FR.21.5). Deliberately fire-and-forget — there is no blocking "ask and wait" counterpart (ruled out as unreliable); a session asks a question by calling `notify_user` and then ending its turn, and the user's plain-text reply resumes the session as an ordinary prompt. Reserved for the top-level session only (FR.21.20): a Worker Session's call is dropped outright before any channel (FR.21.19, FR.21.5) and never even told the tool exists (`InstructionOptionsModel.IsWorkerSession` suppresses the guidance line); a Task-tool subagent sharing its parent's session token is discouraged via the tool's own description and the `cmx-orchestration` skill, since Tessyn has no server-side way to distinguish it from its parent. |
| **Desktop Toast** (`INotificationService`, `WindowsNotificationService`) | The Windows toast shown for every `notify_user` call from a top-level session (FR.21.5) — the desktop copy of the Telegram Mention Ping, sent alongside it. Titled with the session's topic name (`{directory label} / {session name}`), body = the message (truncated), gated on `NotificationsEnabled`; clicking it selects the session. Never shown for turn completion — before ISSUE.012 it fired on every completed scheduled turn, via the since-deleted `CompositeNotificationService`. |
| **Session Completion Sound** (`PlayCompletionSound`) | A per-session, opt-in audible cue (FR.22, default on) that plays when the interactive command bar's "Claude is thinking…" state clears on natural turn completion — for both One-shot Mode and Streaming Session Mode — but not on user-initiated Stop. Toggled via a bell (🔔) button beside the Streaming Session Mode toggle. The only turn-completion signal Tessyn gives (neither the Desktop Toast nor Telegram announces turn completion since ISSUE.012); deliberately silent for turns started by the scheduler, orchestration or Telegram. |
| **`ISessionSoundService`** | The app-lifetime singleton (FR.22.3, FR.22.4) that enforces the Session Completion Sound's per-`NodeId` throttle (`AppSettingsModel.SessionCompletionSoundThrottleSeconds`, default 180s) and plays `AppSettingsModel.SessionCompletionSoundFile` via the Win32 `winmm.dll` `PlaySound` API — chosen to avoid adding a NuGet audio package. Also enumerates the Windows default sound library (`%WINDIR%\Media\*.wav`) for the Settings sound picker. |
